Before building the Doctor Dashboard, we should lock down exactly what data it receives, how it is structured, what is generated by AI, what comes directly from sources, and what the doctor is allowed to edit.

The key principle is:

Do not send one giant AI-generated paragraph to the doctor.
Send a structured clinical record, where every important fact has a source, status, and evidence reference.

1. Overall data flow

Your system should work like this:

PATIENT KIOSK
│
├── Patient demographics
├── Current interview
├── Voice / touch answers
├── ABHA / ABDM records
├── Phone-uploaded documents
├── OCR text
├── Structured document extraction
├── Medical timeline
├── Attention flags
└── AYUSH information
          │
          ▼
     BACKEND ORCHESTRATION
          │
          ├── Validate
          ├── Normalize
          ├── Fuse
          ├── Filter complaint-relevant data
          └── Generate clinical-history draft
          │
          ▼
     STRUCTURED JSON
          │
          ▼
     DOCTOR DASHBOARD

The Doctor Dashboard should fetch a structured JSON payload from the server.

The browser should not independently combine:

ABDM records
OCR
interview
AI output

The server should do that.

2. What exactly is sent to the Doctor Dashboard?

I recommend the dashboard API returns one canonical object roughly like:

{
  "schemaVersion": "1.0",
  "session": {},
  "patient": {},
  "consultation": {},
  "clinicalHistory": {},
  "relevantHistory": {},
  "timeline": {},
  "attentionFlags": [],
  "documents": [],
  "sources": [],
  "conflicts": [],
  "ayush": {},
  "verification": {},
  "generatedAt": "..."
}

This is the dashboard view model.

It is NOT the same thing as the raw database model.

3. Patient section

The doctor needs basic identification information.

Example:

{
  "patient": {
    "patientId": "PAT-001",
    "name": "Ravi Kumar",
    "age": 46,
    "dateOfBirth": "1980-03-12",
    "gender": "male",
    "hospitalNumber": "HSP-100245",
    "abhaReference": "ABHA-XXXX",
    "department": "General Medicine",
    "language": "ta"
  }
}
Important

Do not expose unnecessary personal information.

Only include what the doctor actually needs.

4. Consultation section

This tells the doctor why the patient is here right now.

{
  "consultation": {
    "complaint": "Stomach pain",
    "patientStatement": "I've had stomach pain for around three weeks. It gets worse after eating.",
    "duration": "3 weeks",
    "startedAt": null,
    "status": "current"
  }
}

Notice that the patient's original words are preserved.

That's useful for Source Truth.

5. Clinical History section

This is the main structured history.

I would organize it as:

{
  "clinicalHistory": {
    "chiefComplaint": {},
    "historyOfPresentIllness": {},
    "pastMedicalHistory": [],
    "pastSurgicalHistory": [],
    "medications": [],
    "allergies": [],
    "familyHistory": [],
    "personalSocialHistory": {},
    "reviewOfSystems": {},
    "investigations": []
  }
}
Example
{
  "historyOfPresentIllness": {
    "onset": {
      "value": "3 weeks ago",
      "status": "reported"
    },
    "duration": {
      "value": "3 weeks",
      "status": "reported"
    },
    "severity": {
      "value": "severe",
      "status": "reported"
    },
    "aggravatingFactors": [
      "Eating"
    ],
    "location": {
      "value": null,
      "status": "not_reported"
    }
  }
}

The key thing is:

Do not use null alone.

Distinguish:

not_reported
unknown
not_applicable
reported
conflicting
requires_review

Because:

"Patient did not mention this"

is not the same as:

"Patient said no."

6. Every fact needs provenance

This is the most important part of your whole Doctor Dashboard.

Suppose:

{
  "medication": "Amlodipine 5 mg"
}

Don't send just that.

Send:

{
  "name": "Amlodipine",
  "strength": "5 mg",
  "frequency": "once daily",

  "provenance": [
    {
      "sourceType": "patient_interview",
      "answerId": "ANS-123",
      "questionId": "current_medications"
    },
    {
      "sourceType": "abdm",
      "recordId": "ABDM-884"
    },
    {
      "sourceType": "document",
      "documentId": "DOC-44",
      "extractionId": "EXT-91"
    }
  ]
}

Then the doctor can click:

Amlodipine

and see:

SOURCE TRUTH

🗣 Patient Interview
Question:
"What medications are you currently taking?"

Answer:
"Amlodipine 5 mg once daily."

🏥 ABDM
Medication record:
Amlodipine 5 mg

📄 Prescription
Date:
2024

Extracted text:
Amlodipine 5 mg once daily

That's your trust feature.

7. Source types

Use your existing provenance architecture.

Conceptually:

patient_interview
document
abdm

You can also have:

derived

But derived never means "new medical fact."

Example:

derived:
"Medication history contains multiple sources"

The underlying sources remain the actual evidence.

8. Status of each fact

Every important fact should carry a status.

For example:

reported
confirmed
unconfirmed
conflicting
requires_review
patient_corrected
physician_verified

Example:

{
  "name": "Metformin",
  "status": "conflicting"
}

because:

Patient:
Currently taking Metformin

ABDM:
Marked discontinued

The dashboard should show:

⚠️ Conflicting information — physician review required.

9. Current vs historical

This should be explicit in the JSON.

For example:

{
  "temporalStatus": "historical"
}

vs

{
  "temporalStatus": "current"
}

This prevents the system from accidentally treating:

"Medication listed in a 2022 record"

as:

"Patient is taking this now."

10. Complaint-centric relevant history

This is where your Phase 15A feature becomes important.

Don't send the full history as the primary consultation view.

Send something like:

{
  "relevantHistory": {
    "complaint": "stomach pain",
    "status": "found",
    "records": [
      {
        "title": "Gastritis",
        "date": "2024",
        "relevance": "direct",
        "provenance": [...]
      },
      {
        "title": "Gastric medication",
        "date": "2024",
        "relevance": "related",
        "provenance": [...]
      }
    ]
  }
}

If there is nothing:

{
  "relevantHistory": {
    "complaint": "stomach pain",
    "status": "none_found",
    "records": []
  }
}

The dashboard should then say:

No relevant previous history found for this complaint.

Not show a giant empty timeline.

11. Timeline should be optional

The server should tell the UI what visualization makes sense.

For example:

{
  "timeline": {
    "displayMode": "timeline",
    "events": []
  }
}

Possible modes:

none
single_card
compact_list
timeline
mind_map

So:

Nothing relevant
"displayMode": "none"
One relevant record
"displayMode": "single_card"
Many related events
"displayMode": "timeline"

This directly implements your requirement that timeline should only appear when useful.

Example:

          "questionId": "q13",

The doctor sees:

Potentially urgent symptoms reported.

Not:

"Patient has heart attack."

13. Documents

The doctor should get document metadata and access references.

Example:

{
  "documents": [
    {
      "documentId": "DOC-101",
      "type": "prescription",
      "date": "2024-06-18",
      "fileName": "prescription.jpg",
      "ocrStatus": "completed",
      "extractionStatus": "completed",
      "source": "document"

  ]

When opening it:

Document
↓
Original document
↓
OCR text
↓
Extracted facts

Do not dump OCR text into the main dashboard.

14. ABDM records

ABDM information should similarly remain traceable.

Example:

{
  "abdm": {
    "records": [
      {
        "recordId": "ABDM-001",

16. AI-generated summary

This is where we need a very important distinction.

The dashboard should receive:

{
  "generatedHistory": {
    "status": "draft",
    "generatedBy": "gemini",
    "generatedAt": "...",
    "content": {},
    "sourceReferences": []
  }
}

The status is:

AI DRAFT — NOT PHYSICIAN VERIFIED

The doctor can compare the draft against the structured evidence.

17. Don't send only one giant summary

This is what I don't recommend:

{
  "summary": "The patient is a 45-year-old with..."
}

Because then your doctor has no idea:

What came from patient
What came from ABDM
What came from documents
What AI inferred
What is conflicting

Instead:

STRUCTURED DATA
+
PROVENANCE
+
EVIDENCE
+
AI DRAFT

Then render the readable summary from that.

20. Doctor editing

The dashboard should separate:

AI/Draft state

from:

Physician verified state

For example:

{
  "verification": {
    "status": "draft",
    "physicianId": null,
    "verifiedAt": null
  }
}

After the doctor verifies:

{
  "verification": {
    "status": "physician_verified",
    "physicianId": "...",
    "verifiedAt": "..."

}

Don't let "AI generated" automatically become "verified."

22. Recommended API

I recommend one main dashboard endpoint:

GET /api/doctor/sessions/:sessionId

It can return:

{
  "patient": {},
  "consultation": {},
  "clinicalHistory": {},
  "relevantHistory": {},
  "timeline": {},
  "attentionFlags": [],
  "documents": [],
  "ayush": {},
  "generatedHistory": {},
  "conflicts": [],
  "verification": {}
}

Then optional detail APIs:

GET /api/doctor/sessions/:sessionId/sources/:recordId
GET /api/doctor/sessions/:sessionId/documents/:documentId

Only create these if the main payload shouldn't contain enough source detail.

23. The single most important architecture rule

Your Doctor Dashboard should never trust a human-readable AI summary as the source of truth.

The hierarchy should be:

SOURCE EVIDENCE
      ↓
STRUCTURED FACTS
      ↓
FUSED / RELEVANT RECORD
      ↓
AI-GENERATED DRAFT
      ↓
DOCTOR REVIEW
      ↓
PHYSICIAN-VERIFIED HISTORY

Not:

SOURCE
   ↓
AI
   ↓
"Trust me"

That distinction is something you can explain very strongly to SIH judges.

MORE INFO 
1. The dashboard is a separate doctor workstation

It should be completely separate from the patient kiosk:

/kiosk                    → Patient
/kiosk/interview          → Patient
/kiosk/documents          → Patient phone/kiosk flow

/doctor                   → Doctor
/doctor/patient/[id]      → Individual patient review

The doctor dashboard should be designed primarily for a desktop/laptop/tablet, not the kiosk touchscreen.

2. Doctor should see the most important things first

The first screen should not dump the entire history.

A good priority hierarchy is:

1. 🚨 Attention / urgent flags
2. Current complaint
3. Key HPI
4. Relevant previous history
5. Medications + allergies
6. Relevant investigations
7. Timeline
8. Documents
9. AYUSH
10. Full details / source evidence

The doctor should understand the case within 10–20 seconds, then drill deeper.

3. "What changed today?"

This would be a very useful feature.

The dashboard can distinguish:

CURRENT VISIT
vs
PREVIOUS HISTORY

For example:

New this visit

Abdominal pain × 3 weeks
Worse after meals
New vomiting reported

This helps the doctor immediately understand the current reason for consultation.

4. Relevant history should be complaint-centric

You already built this in Phase 15A.

The dashboard should primarily show:

History relevant to current complaint

with a secondary option such as:

View complete available history

This prevents the physician from being overwhelmed by unrelated records.

5. "Why is this here?" should always be possible

Every important field should support:

Click → Source Truth

For example:

Medication: Metformin

🗣 Patient
📄 Prescription
🏥 ABDM

[Why is this shown?]

Then show the exact evidence.

This is one of your strongest differentiators.

6. AI content needs a clear visual label

The doctor should immediately know what was generated by AI.

For example:

🧠 AI-GENERATED DRAFT

and:

Requires physician verification

AI-generated content should never visually look identical to physician-confirmed information.

After verification:

✅ Physician Verified

The doctor should be able to correct incorrect extraction rather than being forced to accept it.

8. Don't overwrite original evidence when doctor edits

This is extremely important.

Suppose AI extracted:

Metformin 500 mg

Doctor changes it to:

Metformin 500 mg — currently not taking

Do not modify the original OCR/ABDM evidence.

Instead:

Original source:
📄 Prescription
"Metformin 500 mg"

Physician correction:
"Currently not taking"

Final status:
✅ Physician verified

This maintains an audit trail.
